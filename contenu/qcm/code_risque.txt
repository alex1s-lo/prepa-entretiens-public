=== sql-group-by
+ `GROUP BY ticker HAVING COUNT(*) >= 200 ORDER BY moyenne DESC`
  `HAVING` filtre après l'agrégation.
- `WHERE COUNT(*) >= 200`
  `WHERE` s'applique avant le regroupement : un agrégat y est interdit.
- `GROUP BY ticker, jour`
  On obtiendrait une ligne par jour.
- `ORDER BY` avant `GROUP BY`
  L'ordre des clauses SQL est imposé.

=== sql-fenetre
+ `AVG(r) OVER (PARTITION BY ticker ORDER BY jour ROWS BETWEEN 19 PRECEDING AND CURRENT ROW)`
  Une fonction de fenêtre garde toutes les lignes.
- `GROUP BY ticker` avec `AVG(r)`
  Une seule ligne par ticker.
- `ROWS BETWEEN 20 PRECEDING AND CURRENT ROW`
  Cela fait 21 observations.
- Sans `PARTITION BY`
  Les tickers se mélangeraient.

=== sql-rendement-lag
+ `cloture / LAG(cloture) OVER (PARTITION BY ticker ORDER BY jour) - 1`
  La première ligne de chaque ticker vaut NULL.
- `LEAD(cloture)` à la place de `LAG`
  Regarde le jour suivant : regard vers le futur.
- `LAG` sans `PARTITION BY`
  Le premier jour d'un ticker utiliserait le dernier d'un autre.
- `cloture - LAG(cloture)`
  C'est une variation absolue, pas un rendement.

=== sql-jointures
+ Au moins 1 000 lignes (exactement 1 000 si `clients.id` est unique)
  `LEFT JOIN` garde toutes les lignes de gauche.
- 100
  C'est la taille de la table de droite.
- 100 000
  C'est un produit cartésien.
- Au plus 100
  `INNER` ou `LEFT`, on ne descend pas sous 1 000 avec une clé unique.

=== sql-dedoublonnage
+ `ROW_NUMBER() OVER (PARTITION BY ticker ORDER BY horodatage DESC)` puis garder le rang 1
  Robuste même en cas d'égalité gérée par l'ordre.
- `SELECT DISTINCT ticker, prix`
  Garde toutes les combinaisons distinctes.
- `MAX(prix)` par ticker
  Donne le plus haut prix, pas le dernier.
- `GROUP BY ticker` avec `prix` non agrégé
  Invalide ou non déterministe.

=== sql-null
+ `NULL = NULL` est inconnu ; `COUNT(col)` ignore les NULL ; `NOT IN` avec un NULL ne renvoie rien
  Utiliser `IS NULL` et `COALESCE`.
- `NULL = NULL` est vrai
  C'est inconnu.
- `COUNT(*)` ignore les NULL
  C'est `COUNT(col)`.
- `AVG` compte les NULL comme des zéros
  Il les ignore.

=== cpp-virtuel
+ Appel via la vtable : une indirection, pas d'inlining ; coût faible mais gênant en très basse latence
  Alternatives : templates (CRTP).
- Les fonctions virtuelles sont résolues à la compilation
  À l'exécution.
- Elles copient l'objet
  Sans rapport.
- Elles sont gratuites
  L'indirection empêche souvent l'inlining.

=== cpp-comportement-indefini
+ Une opération sans résultat imposé par la norme : débordement d'entier signé, accès hors limites, pointeur libéré
  Le compilateur peut supposer qu'il n'arrive jamais.
- Une erreur de compilation
  Il compile souvent sans avertissement.
- Un plantage garanti
  Il peut sembler marcher.
- Un débordement d'entier non signé
  Lui est bien défini (modulo).

=== cpp-move
+ Voler les ressources d'un objet temporaire ; `std::move` est un simple transtypage en rvalue
  Le déplacement évite des copies coûteuses.
- `std::move` déplace physiquement l'objet
  Il ne fait que convertir le type.
- Le déplacement copie toujours
  Il transfère les ressources.
- L'objet d'origine est détruit immédiatement
  Il reste valide mais dans un état non spécifié.

=== py-copie
+ `[[1, 0, 0], [1, 0, 0], [1, 0, 0]]`
  Les trois lignes sont la même liste.
- `[[1, 0, 0], [0, 0, 0], [0, 0, 0]]`
  Ce serait le cas avec `[[0] * 3 for _ in range(3)]`.
- Une erreur
  Le code est valide.
- `[[1, 1, 1], [0, 0, 0], [0, 0, 0]]`
  Le `* 3` intérieur copie des entiers, pas des références partagées problématiques.

=== algo-fusion-intervalles
+ Trier par début puis fusionner en un passage : $O(n \log n)$
  Un intervalle chevauche le précédent si son début est avant la fin courante.
- Comparer toutes les paires
  $O(n^2)$ et compliqué.
- Trier par fin uniquement
  Ne garantit pas une fusion correcte en un passage.
- Fusionner sans trier
  Les chevauchements non voisins échappent.

=== algo-k-plus-grands
+ Un tas min de taille $k$ : $O(n \log k)$
  On compare à la plus petite des $k$ gardées.
- Trier : $O(n \log n)$, optimal
  Correct, mais le tas fait mieux pour $k$ petit.
- Un tas max de taille $n$ puis $k$ extractions
  $O(n + k\log n)$ : bien, mais mémoire $O(n)$.
- Parcourir $k$ fois la liste
  $O(nk)$.

=== risque-liquidite

  C'est la liquidité de financement, autre notion.
- Il est nul pour les grandes positions
  Il augmente avec la taille.
- Il est inclus dans toute VaR standard
  La VaR standard suppose une liquidation sans coût.
