=== sql-group-by
+ `GROUP BY ticker HAVING COUNT(*) >= 200`, puis `ORDER BY`
  `HAVING` filtre après l'agrégation.
- `WHERE COUNT(*) >= 200` avant le `GROUP BY ticker`
  `WHERE` s'applique avant le regroupement : un agrégat y est interdit.
- `GROUP BY ticker, jour HAVING COUNT(*) >= 200`
  On obtiendrait une ligne par jour.
- `ORDER BY` avant `GROUP BY`
  L'ordre des clauses SQL est imposé.

=== sql-fenetre
+ `AVG(r) OVER (PARTITION BY ticker ORDER BY jour ROWS 19 PRECEDING)`
  Une fonction de fenêtre garde toutes les lignes ; `ROWS 19 PRECEDING` s'écrit aussi `ROWS BETWEEN 19 PRECEDING AND CURRENT ROW` (20 observations).
- `GROUP BY ticker` avec `AVG(r)`
  Une seule ligne par ticker.
- `AVG(r) OVER (PARTITION BY ticker ORDER BY jour ROWS 20 PRECEDING)`
  Cela fait 21 observations.
- `AVG(r) OVER (ORDER BY jour ROWS 19 PRECEDING)`, sans partition
  Les tickers se mélangeraient.

=== sql-rendement-lag
+ `cloture / LAG(cloture) OVER (PARTITION BY ticker ORDER BY jour) - 1`
  La première ligne de chaque ticker vaut NULL.
- `cloture / LEAD(cloture) OVER (PARTITION BY ticker ORDER BY jour) - 1`
  Regarde le jour suivant : regard vers le futur.
- `cloture / LAG(cloture) OVER (ORDER BY jour) - 1`
  Le premier jour d'un ticker utiliserait le dernier d'un autre.
- `cloture - LAG(cloture)`
  C'est une variation absolue, pas un rendement.

=== sql-jointures
+ Au moins 1 000
  `LEFT JOIN` garde toutes les lignes de gauche ; exactement 1 000 si `clients.id` est unique, plus si une clé se répète à droite.
- Exactement 100
  C'est la taille de la table de droite.
- 100 000 (une par couple)
  C'est un produit cartésien.
- Au plus 100, une par client
  `INNER` ou `LEFT`, on ne descend pas sous 1 000 avec une clé unique.

=== sql-dedoublonnage
+ `ROW_NUMBER()` par ticker, du plus récent, puis le rang 1
  Robuste même en cas d'égalité gérée par l'ordre.
- `SELECT DISTINCT ticker, prix ORDER BY horodatage DESC`
  Garde toutes les combinaisons distinctes.
- `SELECT ticker, MAX(prix) ... GROUP BY ticker`
  Donne le plus haut prix, pas le dernier.
- `GROUP BY ticker` en gardant la colonne `prix` sans agrégat
  Invalide ou non déterministe.

=== sql-null
+ `NULL = NULL` est inconnu, et `NOT IN` avec un NULL ne renvoie rien
  De plus, `COUNT(col)` ignore les NULL. Utiliser `IS NULL` et `COALESCE`.
- `NULL = NULL` est vrai, donc les jointures sur NULL fonctionnent
  C'est inconnu.
- `COUNT(*)` ignore les lignes où une colonne vaut NULL
  C'est `COUNT(col)`.
- `AVG` compte les NULL comme des zéros, ce qui baisse la moyenne
  Il les ignore.

=== cpp-virtuel

  Coût faible, mais gênant en très basse latence ; alternative : templates (CRTP).

  À l'exécution.

  Sans rapport.

  L'indirection empêche souvent l'inlining.

=== cpp-comportement-indefini

- Une erreur que le compilateur signale toujours à la compilation
  Il compile souvent sans avertissement.
- Un plantage garanti à l'exécution, avec un message d'erreur
  Il peut sembler marcher.
- Un débordement d'entier non signé

=== cpp-move
+ Voler les ressources d'un objet ; `std::move` n'est qu'un transtypage
  `std::move` convertit en rvalue ; le constructeur de déplacement évite une copie coûteuse.
- `std::move` déplace physiquement l'objet
  Il ne fait que convertir le type.
- Le déplacement fait une copie profonde, puis libère l'original
  Il transfère les ressources.
- L'objet d'origine est détruit immédiatement
  Il reste valide mais dans un état non spécifié.

=== py-copie
+ `[[1, 0, 0], [1, 0, 0], [1, 0, 0]]`
  Les trois lignes sont la même liste.
- `[[1, 0, 0], [0, 0, 0], [0, 0, 0]]`
  Ce serait le cas avec `[[0] * 3 for _ in range(3)]`.
- Une erreur
  Le code est valide.
- `[[1, 1, 1], [0, 0, 0], [0, 0, 0]]`
  Le `* 3` intérieur copie des entiers, pas des références partagées problématiques.

=== algo-fusion-intervalles
+ Trier par début puis fusionner en un passage
  $O(n \log n)$ ; un intervalle chevauche le précédent si son début est avant la fin courante.
- Comparer toutes les paires et fusionner celles qui se chevauchent
  $O(n^2)$ et compliqué.
- Trier par fin uniquement
  Ne garantit pas une fusion correcte en un passage.
- Fusionner dans l'ordre d'arrivée, sans trier
  Les chevauchements non voisins échappent.

=== algo-k-plus-grands
+ Un tas min de taille $k$ : $O(n \log k)$
  On compare à la plus petite des $k$ gardées.
- Trier : $O(n \log n)$, optimal
  Correct, mais le tas fait mieux pour $k$ petit.
- Un tas max de taille $n$ puis $k$ extractions
  $O(n + k\log n)$ : bien, mais mémoire $O(n)$.
- Parcourir $k$ fois la liste
  $O(nk)$.

=== risque-var-historique

  Seulement ceux de la fenêtre.

=== risque-correlation-crise

  Tester les portefeuilles avec des corrélations stressées.

=== risque-liquidite
+ Ne pas pouvoir déboucler sans faire bouger le prix

- Le risque de manquer de trésorerie seulement

- Il est nul pour les grandes positions, mieux traitées par les courtiers
  Il augmente avec la taille.
- Il est inclus dans toute VaR standard
  La VaR standard suppose une liquidation sans coût.
